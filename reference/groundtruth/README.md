# Ground truth from Power BI Desktop

Differential tests that compare DashCraft one-to-one with Power BI Desktop
([ADR-0011](../../docs/adr/0011-desktop-ground-truth.md)). Desktop's local Analysis Services
engine answers the DAX queries of a corpus; the answers are committed as recordings; the test
runs the same queries through DashCraft and compares them value by value.

```sh
cargo test -p pbi-session --test groundtruth -- --nocapture   # compare (any OS; SKIPs without recordings)
cargo xtask groundtruth                                       # status: cases, recorded, stale, volatile, ledger, Desktop version
cargo xtask groundtruth --check                               # fails on stale or missing recordings
python scripts/groundtruth/gen_corpus.py --check              # corpora are up to date with their inputs
```

Each run writes a report per suite to `target/tmp/groundtruth/<suite>.md`, and new mismatches as
ready-to-edit ledger entries to `target/tmp/groundtruth/<suite>.proposed.json`.

## Layout

| Path | What |
|---|---|
| `corpus/<suite>.json` | The queries of a suite: `id`, `query`, optionally `volatile` (reason), `metadata` (an `INFO.VIEW.*` adapter), `viewAs` (DashCraft's RLS view) and `desktopRoles` (the roles Desktop connects with). Generated by `scripts/groundtruth/gen_corpus.py`; ids come from the case content, so adding a case leaves the other recordings valid |
| `recordings/<suite>.json` | What Desktop returned: Desktop and engine version, culture, date; per case `columns` and `rows`, or `error`, or (volatile) `columns` and `rowCount` |
| `deviations.json` | The ledger of accepted differences (below) |
| `fixtures/dax-lab/` | The PBIP of the `dax-functions` suite, generated by `scripts/groundtruth/gen_dax_lab.py` from the models of `crates/pbi-dax/tests/functions.rs` |
| `gt4/<session>/`, `gt4/deviations.json` | Desktop-saved TMDL before and after scripted edits, the edits, and the accepted differences of DashCraft's save ([below](#writer-form-gt-4-dashcraft-saves-what-desktop-saves)) |

| Suite | Fixture | Cases | What |
|---|---|---|---|
| `acme-metadata` | Acme | 5 | Tables, columns, measures, format strings, relationships (`INFO.VIEW.*`) |
| `acme-tables` | Acme | 11 | Every table, every row and column after refresh (M, calculated columns and tables) |
| `acme-measures` | Acme | 601 | Every measure at the grand total, per page and slicer filter of `expected.json`, and grouped by dimensions |
| `acme-calcgroup-rls` | Acme | 26 | Calculation items, and every RLS role and user of `expected.json` |
| `acme-visuals` | Acme | 9 | `SUMMARIZECOLUMNS` queries shaped like the report's visuals |
| `format` | Acme | 747 | `FORMAT` with every format string of the model and the standard and custom formats |
| `dax-functions` | dax-lab | 552 | The cases of `crates/pbi-dax/tests/functions.rs` |
| `dax-lab-tables` | dax-lab | 5 | The dax-lab tables |
| `samples-*` | Microsoft samples | 286 | Metadata, row counts, column aggregates, small tables and every measure of three MIT PBIX samples (VertiPaq decoding against Desktop) |

`cargo xtask groundtruth` prints the current counts.

### Value encoding

A row is a JSON array in column order. `null` is BLANK; `true`/`false`; an integer is a JSON
integer; a double always has a `.` or exponent (`1.0`), with `{"double":"NaN"}` and
`{"double":"Infinity"}` for the special values; a fixed decimal (currency) is
`{"decimal":"12.3400"}`; a date/time is `{"dateTime":"2024-01-05T00:00:00.000"}` (no time zone);
text is a JSON string.

### Comparison

Numbers compare across types with a 1e-9 relative or absolute tolerance, fixed decimals exactly;
BLANK equals only BLANK; text exactly; date/times to the millisecond. Rows are a multiset unless the
query has `ORDER BY`. Errors compare by parity: both sides must fail, messages are not compared.
Volatile cases (the clock, random numbers, the signed-in user, refresh time) compare columns and
row count only. A recording whose `query` differs from the corpus is stale and fails.

### Deviation ledger

A mismatch fails the test unless `deviations.json` lists it:

```json
{ "suite": "dax-functions", "case": "window/1a2b3c4d", "kind": "bug", "reason": "…", "gap": "DAX engine" }
```

`kind` is `bug` (DashCraft is wrong; link the `docs/GAPS.md` area in `gap`), `unsupported`,
`byDesign` (an intended difference, such as float summation order) or `lenient` (DashCraft accepts
what Desktop rejects). `case` may end in `*` to match a prefix. An entry whose case now matches
fails the test too: delete it. The ledger only shrinks; a new feature fixes a mismatch instead of
adding a `bug` entry.

## Recording

Windows only. Recording needs neither credentials nor network access to data, and nothing about
the machine may end up in a committed file (no user names, paths, accounts or screenshots).

**Prerequisites.** Power BI Desktop (Microsoft Store or installer), PowerShell 7 (`pwsh`), Python 3
and a Rust toolchain. Desktop's culture must be en-US (the recorder checks `USERCULTURE()` and
stops otherwise). The first run downloads the ADOMD.NET client package from NuGet into
`target/groundtruth/tools/` (gitignored).

**1. Prepare the fixtures.**

```powershell
python scripts/groundtruth/make_desktop_variant.py   # Acme copy Desktop can refresh: target/groundtruth/acme-desktop/
python scripts/groundtruth/gen_dax_lab.py            # only after changing the generator
python scripts/groundtruth/gen_corpus.py             # only after changing a corpus input
```

The Acme copy replaces the offline `AzureStorage.Blobs` source by `Folder.Contents` of the local
`data/` folder (a `DataFolder` parameter with an absolute path, hence only under `target/`) and
adds static copies of the dynamic RLS roles (`GT <role> <user>`), because Desktop's engine only
impersonates Windows accounts. The model, measures and reports are otherwise byte-identical.

**2. Open the fixtures in Desktop** (one window each, as many as needed at once):
`target/groundtruth/acme-desktop/AcmeOutfitters.pbip`,
`reference/groundtruth/fixtures/dax-lab/DaxLab.pbip`, and the samples
`reference/samples/microsoft/*.pbix`. Desktop's engine listens on a random localhost port per
window; `Find-GtInstance` picks the window whose model has the suite's `requiresTables`.

**3. Record.**

```powershell
pwsh -NoProfile -File scripts/groundtruth/Record-GroundTruth.ps1 -Refresh             # every suite
pwsh -NoProfile -File scripts/groundtruth/Record-GroundTruth.ps1 -Refresh -Corpus reference/groundtruth/corpus/format.json
```

`-Refresh` refreshes each model once through TMSL first (no UI); `-Port` picks an engine by hand;
`-OutDir` records elsewhere (writer checks below).

**4. Compare and review.** Run the test, read `target/tmp/groundtruth/<suite>.md`, fix DashCraft
or add a reasoned ledger entry, and review the recording diff like a snapshot change. Commit
corpus, recordings and ledger together.

**On a new Desktop release** re-record everything (step 3), then compare the old and new
recordings: `python scripts/groundtruth/compare_recordings.py <old dir> reference/groundtruth/recordings`.
A changed value is a Desktop behaviour change: note it in `docs/DEVLOG.md`.

## Writer form (GT-4): DashCraft saves what Desktop saves

```sh
cargo test -p pbi-ops --test save edits_save_like_power_bi_desktop
```

`gt4/<session>/` holds a model's `definition/` folder as Desktop saved it before (`before/`) and
after (`after/`, only the files Desktop rewrote) a list of edits, written as registry steps
(`edits.json`; the last is `doc.save`). The test copies Acme, puts `before/` over its
`definition/`, opens it with the blob map, runs the steps and compares: DashCraft must write
exactly the files Desktop wrote, and every definition file must equal Desktop's byte for byte once
identifiers new in `after/` read `<new id>` and the entries of `gt4/deviations.json` are applied.
Each entry names the session, Desktop version, file, Desktop's lines, DashCraft's lines and the
reason; an entry that no longer applies fails the test. Per ADR-0014 the list holds at most 20
entries and only shrinks, except for reviewed changes of a new Desktop release. The files are
stored as Desktop wrote them (CRLF; `-text` in `.gitattributes`).

**Session s24** (Desktop 2.159). On a copy of the Desktop project of Acme: four measures on
`Orders` (a plain one; one with a format string, display folder, description and hidden; a
multi-line `VAR` expression; a name with an apostrophe), the calculated column
`Orders[GT4 Margin]`, the calculated table `GT4 Regions` (`DISTINCT(Stores[Region])`), the
hierarchy `Stores[GT4 Channel Region]` and the relationship `Stores[Region]` → `GT4 Regions[Region]`.
The workstation was locked, so the objects were created over Desktop's engine connection with the
Tabular Object Model, with the properties Desktop's UI gives them (lineage tags, summarize-by and
its `SummarizationSetBy` annotation, inferred data types), and saved with Desktop's own Save button
(UI Automation): Desktop wrote the TMDL. Before committing, the Desktop copy's local source
(`Source = AcmeBlobs,`) was set back to Acme's `AzureStorage.Blobs(StorageContainerUrl)` line so
the files open with the blob map; `before/` has no `expressions.tmdl` (Acme's is used). What
Desktop does, and DashCraft now does too:

- Line ends CRLF, no BOM, every file ending with a blank line. DashCraft keeps the line ends and
  blank last line of the files it edits, and a new file takes the project's prevailing style; a
  conversion to a new project stays LF.
- Property order. Column: `dataType`, `isHidden`, `isKey`, `formatString`, `displayFolder`,
  `lineageTag`, `sourceLineageTag`, `dataCategory`, `summarizeBy`, `isNameInferred`,
  `isDataTypeInferred`, `sourceColumn`, `sortByColumn`, then a blank line before annotations.
  Measure: `formatString`, `isHidden`, `displayFolder`, `lineageTag`, `dataCategory`, then a blank
  line before `formatStringDefinition` and annotations. Relationship: `isActive`,
  `crossFilteringBehavior`, `joinOnDateBehavior`, `relyOnReferentialIntegrity`,
  `securityFilteringBehavior`, `fromCardinality`, `toCardinality`, `fromColumn`, `toColumn`.
- New measures and columns go after the table's last measure or column.
- Calculation items carry no `ordinal`: Desktop writes them in ordinal order and its TMDL reader
  numbers them by position, ignoring even an explicit `ordinal` (the JSON form keeps explicit
  ordinals). DashCraft numbered items without an `ordinal` -1; it now numbers them by position
  (the test also asserts `EVALUATE 'Time Calc'` equals the `time-calc` recording). An explicit
  `ordinal` still wins, which differs from Desktop only for TMDL whose explicit ordinals are out of
  document order (hand-written; Desktop never writes it).

The two deviations: Desktop leaves out the data type it infers for a calculated column and for a
calculated table's column; DashCraft writes it with `isDataTypeInferred`, so a reopened project
has the column's type before a refresh.

**Desktop opens DashCraft's save (GT-6 s24).** Put DashCraft's five saved files into a copy of
Desktop's `before` project (the source line set back to `AcmeBlobs`) and open it in Desktop 2.159:
no dialog, and every new object is there as written (`INFO.VIEW.*`): the four measures with their
properties, `GT4 Margin` as a number, `GT4 Regions` with its column, the hierarchy, and the
relationship (many to one, single direction). After a refresh, Desktop's values for the new
measures, column and table (grand total, by region of the new table, by channel and region) equal
DashCraft's on the same queries up to floating-point summation order, and `'Time Calc'` returns
ordinals 0 to 3 in both.
