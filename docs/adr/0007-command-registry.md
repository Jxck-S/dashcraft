# ADR-0007: One command registry for the CLI, the RPC server, the app and agents

- Status: Accepted
- Date: 2026-10-22
- Deciders: pbiview maintainers
- Related: [ADR-0001](0001-ui-tauri-svelte.md), [ADR-0004](0004-desktop-ready-architecture.md), [ADR-0006](0006-interaction-state.md); research: [photocraft-review.md](../research/photocraft-review.md) §B, [craft-office-apps-review.md](../research/craft-office-apps-review.md) Tier 2 #8, #9

## Context

pbiview's capabilities were reachable through two hand-written surfaces: the `pbiview` subcommands (clap structs and per-command JSON) and the app's Tauri commands (`app/src-tauri/src/{commands,canvas,data}.rs`, typed IPC). Each re-implemented argument validation, name resolution (reports, pages, tables), refresh orchestration, error mapping and DTOs. A third surface (automation, AI agents through MCP) would have added a third copy.

The *Craft apps (PhotoCraft and its siblings) solve this with one command registry (`CommandSpec { id, label, params, run }`) dispatched identically by the UI, the CLI, a JSON control protocol and an MCP server; agents are confined to read/write roots. Their weak point is loosely typed parameters (a human-readable range string) with JSON Schema only at the MCP boundary.

## Decision

A new library crate, **`pbi-ops`**, holds every capability as a named, typed, schema-described command. It depends on `pbi-core`, `pbi-session`, `pbi-render` (public APIs only), `pbi-engine`, `pbi-model`; nothing below it depends on it. `pbiview-cli` depends on it; the app will.

- **Typed commands.** `trait Command { type Params: DeserializeOwned + JsonSchema; type Output: Serialize + JsonSchema; fn meta() -> CommandMeta; fn run(&Workspace, Params, &Ctx) -> impl Future<Output = Result<Output, OpError>> + Send }`, implemented on unit structs. Parameters are `#[serde(deny_unknown_fields, rename_all = "camelCase")]`; the JSON Schemas (draft 2020-12, `schemars` 1.x: deserialize contract for parameters, serialize contract for results) are generated, never hand-written. Unlike the *Craft registry, the schema is the parameter type, at every layer.
- **Metadata.** `CommandMeta { id (stable, dotted: doc.open), title, summary (one line for people and LLMs), category, mutates_document, long_running, agent_safe, writes_files, since, examples }`. Examples are checked by tests against the parameter type.
- **Registry.** `Registry` stores type-erased `CommandSpec`s (metadata, schemas, `fn(&Workspace, Value, &Ctx) -> BoxFuture<Result<Value, OpError>>`). `Registry::execute(ws, id, params, ctx)` is the only way commands run: it validates parameters before running anything, restricts `Agent` callers to `agent_safe` commands, runs `mutates_document` commands one at a time per `docId` (a per-document async mutex), races the run against the `Ctx` cancellation token, and turns a panic into `internal` (a `catch_unwind` around every poll). `Registry::default_catalog()` is the v1 catalog (43 commands, generated reference in [COMMANDS.md](../COMMANDS.md)); `filter`/`agent_catalog` derive sub-catalogs.
- **Workspace.** `Workspace` (`Send + Sync`) holds open documents keyed by `docId` (`d1`, `d2`, …): `DocEntry { Session, path, options, data generation, canvas state per (report, page) }`, workspace defaults (blob map) and a `PathPolicy`. Data commands load a document's data on first use (`autoRefresh`, default on) so a fresh `doc.open` → `measures.values` works; `data.refresh` reloads explicitly.
- **Context.** `Ctx { CancellationToken, progress sink (ProgressEvent { command, message, fraction, data }), CallerKind (Cli, Rpc, App, Agent) }`.
- **Errors.** `OpError { code, message, data }` with eleven stable string codes (`invalidParams`, `unknownCommand`, `notFound`, `noDocument`, `unsupported`, `pathDenied`, `io`, `query`, `cancelled`, `busy`, `internal`), each mapped to a JSON-RPC integer code and to the CLI exit codes (2 for `query`, else 1; a result with `"ok": false` also exits 2, as the other subcommands do for failed tables, ⚠ measures and visuals).
- **Path policy.** Every path a command reads or writes goes through `PathPolicy::check_read`/`check_write`. Unrestricted for the CLI; with read/write roots (`pbiview serve --read-root/--write-root`, agents) the existing part of a path is canonicalized and must stay inside a root, the missing part may only contain plain names, dangling symlinks and writes through symlinks are refused, blob maps may only map files inside the roots. Check-then-use leaves a TOCTOU window against processes that can write inside the roots; `cap-std`-style handle confinement can replace the check later without changing the API.
- **Surfaces.**
  - `pbiview commands [--json] [--schemas] [--markdown]` (the Markdown is `docs/COMMANDS.md`, kept in sync by a test);
  - `pbiview run <id> [--params JSON] [-p key=value]… [--doc PATH] [--blob-map FILE]` and `pbiview run --batch FILE` (ordered steps sharing a workspace, `"${name.field}"` interpolation, stop on error, not atomic; also the `commands.batch` command);
  - `pbiview serve --stdio`: JSON-RPC 2.0, one message per line; methods are command ids; `progress` notifications; `$/cancel`; bounded concurrency (`busy` beyond the pending limit) with per-document FIFO order for mutating requests. Hand-rolled on Tokio (no RPC framework).
- **Reuse instead of duplication.** The `inspect --json` and `detect --json` DTOs moved from `pbiview-cli` into `pbi-ops` (`inspect_model`, `detect_model`) and gained `JsonSchema` derives; the CLI re-exports them, so `doc.inspect` returns exactly the `inspect --json` schema (version 1) and the CLI output is byte-identical. The app's canvas logic (click, scroll, slicer, matrix, tooltip, selections and effective filters) was adapted into `pbi_ops::canvas` with the same semantics (ADR-0006).

## Alternatives considered

| Option | Why not chosen |
|---|---|
| Keep separate per-surface APIs (clap commands, Tauri commands, a future MCP server) | Three copies of validation, resolution and DTOs drift; every feature has to be wired three times; agents would see a different contract than people. |
| Loosely typed registry (`run: fn(&mut Session, &Value)` plus a parameter doc string, as in PhotoCraft) with schemas only at the MCP edge | No machine-checked contract for the CLI and the app; examples and docs can't be validated. Typed `Params` cost one struct per command and give schemas, validation and docs for free. |
| A declarative macro (`cmd!`) instead of a trait | Saves a few lines per command but hides the types from IDEs and error messages; a trait plus a `BASE` metadata constant keeps commands short enough. Can be added later on top of the trait. |
| `rmcp` (official MCP SDK) as the transport for everything | MCP is one consumer, not the core: the CLI and the app don't speak MCP. Four of the five *Craft siblings hand-roll MCP (newline-delimited JSON-RPC over stdio); our JSON-lines RPC is the same framing, so the MCP adapter is a thin method mapping. The SDK can still be used for that adapter if it pays off. |
| `cap-std` capability handles for the path policy now | Stronger (no TOCTOU) but every reader in `pbi-core`/`pbi-session` opens paths itself; threading `Dir` handles through them is a larger change. The `PathPolicy` API is designed so the implementation can switch. |
| Commands as `Document` commands (ADR-0004) | Those are undoable model edits; the registry is the outer API and includes reads, renders and view state (ADR-0006). Editing commands will be registry commands that apply `Document` commands. |

## Consequences

- A feature is done when its command exists, with metadata, an example and a test through `Registry::execute`; the CLI, RPC and MCP surfaces get it for free.
- **MCP (done, `87c46bb`; [MCP.md](../MCP.md))**: the `pbiview mcp` adapter (`dashcraft mcp` since [ADR-0009](0009-naming-dashcraft.md)) maps `tools/list` to `registry.agent_catalog()` (`id` → name, `summary` → description, `params_schema` → `inputSchema`, `output_schema` → `outputSchema`), `tools/call` to `Registry::execute` with `CallerKind::Agent` and a restricted `PathPolicy`, MCP progress tokens to the `Ctx` progress sink and `notifications/cancelled` to the token. No per-tool code.
- **App migration (done)**: the app holds one `Workspace` (unrestricted path policy, `CallerKind::App`) and runs every domain operation through one generic `ops_execute(requestId, id, params)` Tauri command → `Registry::execute`, with `ops_cancel` (the `Ctx` token) and `Ctx` progress forwarded as `ops://progress` events; TypeScript types and camelCase wrappers for every command are generated from the JSON Schemas into `app/src/lib/ops.gen.ts` (`npm run gen:ops`; a pbi-ops test fails when it is stale). The bespoke data, refresh, DAX, measures and canvas commands and the app's `canvas.rs` / `data.rs` are retired: the app's "newest completed render wins" ordering and legacy report themes moved into `pbi_ops::canvas`, and the front end maps its report / page ids to names. The app keeps only what the registry does not model: UI projections of a document with session `ObjectId`s (`document_views`, `object_details`, `visual_format`, `tmdl_view`, `model_diagram`), the app-wide blob map (installed through the workspace's open hook), File → Recent and window plumbing. See `app/README.md`.
- **CLI migration plan**: existing subcommands keep their byte-identical outputs and schemas (scripts depend on them). New features land as commands first; subcommands are gradually re-implemented as thin wrappers over `Registry::execute` (`detect`, `inspect`, `lint` first) when their output can stay identical.
- Command ids, parameter names and result fields are a public contract: fields are only added within a version; renames need a new id or a `since` bump and a deprecation note.
- `pbi-ops` is in the root `[workspace.dependencies]` (`b196c7c`); `pbiview-cli`, `pbiview-app` and `pbi-ai` take it from there. (When this ADR was written the root manifest was frozen and the CLI used a path dependency.)
- Commands that run other commands carry `CommandMeta::invokes_other_commands` (`commands.batch`); adapters derive their behaviour hints from the whole reachable catalog (MCP annotations) instead of special-casing ids.
- Gaps: no editing commands yet (read-only v1); legacy (PBIX layout, PBIR-Legacy) reports render with the default theme in `render.*` and the CLI's `render` (`canvas.*` resolves their theme files since the app migration moved that logic into `pbi_ops::canvas`, `c03be05`); `doc.open` has no "open bytes" variant; RPC has no TCP transport or authentication (stdio only, the parent process is trusted).
