# ADR-0011: Ground-truth recordings from Power BI Desktop

- Status: Accepted
- Date: 2026-11-05
- Deciders: the project owner
- Related: [ADR-0003](0003-vertipaq-xpress9-cleanroom.md) (clean-room rules),
  [reference/groundtruth/README.md](../../reference/groundtruth/README.md) (how to record),
  [DESKTOP-PLAN.md W1](../DESKTOP-PLAN.md#w1-testing-and-ground-truth) (the plan lists this
  decision as the provisional "ADR-0014"; GT-2 and GT-6 are the sessions it covers)

## Context

Until now, DashCraft's computed output was checked against values we wrote ourselves: the
expected values of the synthetic Acme Outfitters example (computed independently by
`scripts/examples/gen_acme.py`), per-function DAX tests and render snapshots. Each of these
encodes our own reading of how Power BI behaves. When that reading was wrong (BLANK arithmetic,
`FORMAT` rules, blank rows of inactive relationships, …), the tests passed anyway.

A Windows machine with Power BI Desktop is now available. Desktop runs a local Analysis Services
engine that accepts DAX queries over ADOMD.NET on a localhost port. That gives a one-to-one oracle
for every computed value DashCraft produces from a model, without looking inside any Microsoft
binary.

## Decision

1. **Black-box protocol.** Ground truth comes only from Desktop's public surfaces: DAX queries
   sent to its local engine over ADOMD.NET (the documented client library, loaded from Desktop's
   own install folder), files Desktop saves, and messages Desktop shows. No disassembly,
   decompilation, debugging, memory inspection or traffic interception (ADR-0003 rule 3 applies
   unchanged). Inputs are synthetic or licensed: the Acme Outfitters example, the generated
   `dax-lab` fixture and the MIT Microsoft samples.
2. **Corpora and recordings are committed.** `reference/groundtruth/corpus/<suite>.json` lists
   the queries of a suite (generated by `scripts/groundtruth/gen_corpus.py`, checked with
   `--check`); `reference/groundtruth/recordings/<suite>.json` holds what Desktop returned:
   columns, types, rows or the error, the Desktop and engine versions, and a hash of the query.
   These are values computed from synthetic input, so they may be published. Screenshots,
   exports of images and anything showing the recording machine (user name, paths, account)
   stay local.
3. **The comparison is a test.** `crates/pbi-session/tests/groundtruth.rs` runs every case
   through DashCraft on the same fixture and compares value by value: numbers with a 1e-9
   relative or absolute tolerance (fixed decimals exactly), BLANK only equal to BLANK, text
   exactly, date/times to the millisecond, rows as a multiset unless the query orders them, errors
   by parity only (both sides fail; messages differ). A missing recording prints
   `SKIP: <file> missing`; a stale recording (the query hash changed) fails.
4. **Deviation ledger.** A mismatch fails the test unless `reference/groundtruth/deviations.json`
   lists it with a kind (`bug`, `unsupported`, `byDesign`, `lenient`), a reason and optionally the
   `docs/GAPS.md` area. A listed case that now matches also fails, so the ledger only shrinks.
   New features may not add `bug` entries; they fix the bug or record why the difference is
   intended.
5. **Volatile cases** (the clock, random numbers, the signed-in user) record and compare only
   their columns and row count.
6. **Version policy.** Recordings name the Desktop version they came from
   (`cargo xtask groundtruth` lists it). They are re-recorded on a new Desktop release when a
   behaviour change is suspected or before a release; a changed value is a reviewed diff like a
   snapshot change, never a silent update. Recording uses the en-US culture.
7. **Writer checks** (GT-6) use the same recordings: DashCraft's PBIP and PBIT output is opened in
   Desktop, refreshed and recorded into a scratch folder, then compared with the committed
   recordings (`scripts/groundtruth/compare_recordings.py`). Every value must be equal, except
   documented Desktop behaviour on import.

## Alternatives considered

| Option | Why not |
|---|---|
| Keep hand-written expected values only | They share our misunderstandings; the first recordings found 22 differences that all of them had missed |
| Record only in CI on a Windows runner | Desktop needs an installed copy and an interactive GUI session to open a file; hosted runners have neither, and recording per push adds nothing once values are committed |
| Compare error messages too | Messages are localized and change between releases; whether a query fails is the stable fact |
| Store only a hash of each result | A failing comparison could not show the expected value, and reviewers could not read a re-recording diff |
| Use a different engine as the oracle (another tabular server) | Not what users run; Desktop's engine is the behaviour DashCraft promises to match |

## Consequences

- Every feature that changes a computed value adds ground-truth cases and a recording (AGENTS.md
  §8); without a Windows machine the corpus case is added and the recording follows, the test
  SKIPs meanwhile.
- `cargo test -p pbi-session --test groundtruth` runs on every platform from the committed
  recordings; only recording needs Windows.
- The recordings take about 2.3 MB of JSON in the repository, mostly the Acme tables.
- Visual-level queries from Desktop's Performance analyzer (GT-2 visuals) and golden images
  (GT-3) need manual GUI steps; they are described in the ground-truth README and done when
  someone runs them.
